## How the system fits together

### Publication

A variant reaches a customer through `isPromoted` in
`src/lib/vehicleCatalogue/derive.ts`, checked in this order:

1. `overrides.json` `hide` removes it, whatever else says.
2. `overrides.json` `show` publishes it on a named person's authority, and the
   calculator discloses that.
3. `reviews.json` publishes it through the admin review screen.
4. Otherwise `customer_selectable` plus an approved `data_review_log` entry.

**Everything live went through route 2.** Nothing has ever gone through 3 or 4.
The review screen works; it has simply never been the route used.

`SCRIPTS/build-vehicle-catalogue.mjs` turns the database plus overrides into
`catalogue.json` and `vehicle-review-candidates.json`. It runs first in the
Netlify build, so a publication decision reaches customers without a separate
step.

### What the calculator does now

The page leads with tray dimensions, because tray length decides which camper
model a customer is looking at. GVM and current weight sit inside a collapsed
`vehicleDetails` section, because picking a vehicle fills them in.

Selecting a vehicle counts as starting the estimate. Before 3 September it did
not, so the picker would fill GVM and kerb and then show "Not calculated" beside
the customer's own figures.

The enquiry link carries what the customer has already given: `tray_length`,
`vehicle_make_model_year`, `tray_type` and `gvm_upgrade_status`. Everything goes
through one `enquiryUrl()` helper so the custom-solution path and the normal path
cannot drift apart.

Three things it deliberately never sends, each with a test:

- **`requiredTrayLength` as the customer's tray.** It sits next to `trayLength`
  and looks interchangeable. It is the length the *camper* needs.
- **The prose fallbacks.** The summary says "your vehicle" when the field is
  empty, which reads fine in a sentence and is nonsense in a field meant to name
  a vehicle.
- **Empty parameters.** A blank value clears the field on the enquiry form, which
  is worse for the customer than typing it.

## Outstanding

### 1. Six truck families unresearched

Fuso Canter, IVECO T-Way 4x4/6x6, MAN TGS 4x4/6x6, Mercedes-Benz Arocs AWD,
Scania XT 4x4/6x6, Volvo FMX 4x4/6x6. Only the Canter is close to camper
territory; the rest are 20 to 30 tonne trucks.

**Budget for manual document supply, not research.** Every manufacturer site
tried has blocked automated retrieval: ford.com.au 403, hino.com.au 403,
isuzu.com.au TLS certificate failure. The Hino was read from a mirror; the Isuzu,
Sprinter and Crafter sheets were supplied by the owner. Reading and entering a
sheet takes minutes once it is in hand.

A new manufacturer host must be added to `ALLOWED_SOURCE_HOSTS` in
`src/lib/vehicleCatalogue/validate.ts`. Until it is, the build refuses to write
the catalogue at all rather than publish one row from an unapproved source. That
is intended, and it is loud.

### 2. Nine rows the build cannot publish

| Row | Missing |
|---|---|
| `fuso-canter-4x4-wide-cab-current` | chassis mass |
| `iveco-eurocargo-my24-ml150-4x4` | chassis mass |
| `unimog-u4023-au-current` | chassis mass |
| `isuzu-nps-75-175-4x4-day` and `-crew` | model year |
| `vw-crafter-55-*`, four rows | model year |

The four model-year gaps are **deliberate**. `seed.sql` carries an explicit
`UPDATE ... SET model_year_start = NULL` with the comment *"Do not substitute the
research access year for a model year."* The Crafter brochure states none either.
Publishing these is a decision, not a research task: accept an inferred year the
way the RAM 1500 Hurricanes were accepted, or leave them out.

Every other figure on those Isuzu rows was re-read from the manufacturer sheet on
4 September and matched exactly.

### 3. Ford's heavier-options kerb figures

Thirty variants carry an optimistic-kerb disclosure. Twenty-three Rangers are
stored at Ford's lightest-orderable kerb, and the conservative figure Ford also
publishes is not captured.

The database already proves Ford publishes both: 17 Ford rows carry
`Kerb weight with heaviest factory optional equipment` from the 2022MY
specifications. **The one input needed** is the 2026.50MY brochure, page 21,
table "4x4 | Wolftrak, Tremor, Wildtrak, Platinum, Raptor Ranger 2026.50MY
Specifications", row group "Vehicle Masses (kg)".

Do not derive these from the 2022MY rows. A 2026 Wildtrak's lightest kerb of
2331 kg sitting 10 kg under the 2022 Wildtrak's heaviest of 2341 kg is two
different bases coinciding, not a relationship.

The six F-150 rows are flagged on an inference: Ford Australia's published
definition of Kerb Weight, read from the Ranger footnote rather than the F-150
sheet. Confirm it on the same errand.

### 4. Two documents contradict themselves

- The **Sprinter** brochure labels its dual cab pages "RWD Single Cab Chassis" in
  the body style row, while the page title and the `9072…` model type codes say
  dual cab. The title is right.
- Two **Crafter 50** dual cab rows do not reconcile as printed: 2247/2295 and
  2243/2195 against a 4490 kg GVM. Resolve before anyone lowers
  `CHECK (gvm_kg > 4500)`.

### 5. The review screen has never been used

Eighteen rows await review and the screen works, but every live variant was
published by override instead. Using it once would exercise route 3 of the
publication gate for the first time.

### 6. Generated files are committed

`catalogue.json`, `vehicle-review-candidates.json` and `vehicle-variant-index.json`
are generated and committed. Any two branches touching vehicle data conflict in
them, every time. Resolution is always regeneration, never a hand-merge.

The catalogue is generated during the Netlify build, so committing it buys
little. Generating them at build time, or ignoring them, removes the whole class
of conflict.

## Traps

### Merged is not deployed, and deployed is not live

Three separate states. On 3 September a pull request reported MERGED while `main`
was unchanged, because it had been opened against another feature branch that
merged first: **a stacked pull request whose base merges first becomes a no-op.**
Open against `main`, or merge the stack strictly bottom-up.

Check the last state directly: drive the live page, or read Netlify's deploy
record. `state: ready` with a `published_at` is the answer; a green pull request
is not.

### A verification has to be able to fail

Every check needs a control that should **not** change. Six checks passed for the
wrong reason across these two days:

- grepping a page for text that is present but `hidden`
- fetching a bundle without following the redirect, so the body was empty
- matching a string that already existed before the change
- `grep -c` on a single-line XML file, which counts lines and returns 1
- a diff that stringified objects, so every row read `[object Object]`
- counting `"make":"RAM"` on a page that emits each variant twice

And once the opposite: a selector that matched nothing was read as a missing
feature, and reported as a regression that did not exist. **A selector that finds
nothing and a feature that is absent look identical.**

For test suites the method is: **revert the source change and confirm the right
tests fail.** Passing proves nothing on its own.

### Tests can pass against files that are not in the commit

`npm test` passed locally at 406/406 while CI failed at 405/406. The difference
was a regenerated file sitting unstaged in the working tree. Run `git status`
before trusting a green run, and re-run after committing.

### Watch for a signal that exists in the artefact you are checking

A deploy watcher polled the served HTML for a string that only exists in Astro's
bundled JavaScript, and would have polled forever. Markup like `id="gvmUpgrade"`
is a sound signal; anything from a `<script>` block is not.

### The seed is the source of truth, and it drifted once

`bash data/vehicle-selector/build-database.sh` rebuilds the sqlite from
`schema.sql` and `seed.sql`. On 4 September a rebuild silently deleted both Hino
chassis, their source and a coverage row, because that research had been written
into the binary and never back into the seed — **and the script reported
success**.

`tests/vehicle-database-seed.test.ts` now rebuilds into a temporary file and
compares every row, so the next divergence fails. Row counts alone are not
enough: the coverage row differed while the counts matched.

Edit the seed, then rebuild. Never edit the binary and hope.

### Never blind-replace inside a data row

A `replace('NULL, NULL', '2026, NULL', 1)` intended for a model year hit the
first matching pair in a 400-character row, which was `max_body_length_mm`. It
set a chassis's maximum body length to 2026 mm. The build succeeded and the tests
passed; only reverting caught it.

Use a targeted `UPDATE` with an assertion on the affected row count.

### The customer's answer outranks the specification sheet

`tray_type` is derived from the catalogue when the customer has not answered, and
overridden the moment they do. Someone who has fitted a canopy to a tub says so,
and their answer is what reaches Beyond RV. Getting that precedence backwards
would be silent.

### Maximum body length is not a tray length

`max_body_length_mm` is the largest body a chassis is **rated for**. Prefilling it
as a tray would tell a Hino 817 owner their tray is 4865 mm when it might be
4200 mm, and the error runs toward suggesting a camper the vehicle cannot carry.
The calculator states the rating and asks the customer to measure.

Neither Mercedes-Benz nor Volkswagen publishes a maximum rated body length, so
those rows have none. The Crafter's load compartment length is the factory tray,
not a rating, and is recorded in the notes instead.

## Repository practice

`quality` runs `npm run check`, `npm test` and `npm run audit:repository`.
`browsers` runs `npm run test:e2e` across five projects. Both are **required on
`main`** since 4 September.

- `strict` is **false**: a branch need not be rebased onto the latest `main`
  before merging. With `strict` true, every PR would need rebasing whenever
  `main` moved, which on 3 September was several times an hour.
- `enforce_admins` is **false**, so an admin can override in a genuine emergency.
  That escape hatch was used once, on #74 and #75, at the owner's explicit
  instruction; the full suite was then run against merged `main` and passed.

Note that `tsc --noEmit` does **not** check `.astro` script blocks. `astro check`
does, and `npm run check` runs it.
